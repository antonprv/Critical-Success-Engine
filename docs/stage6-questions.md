# Этап 6: вопросы — SDF-часть

Одним пакетом, по подэтапам из `docs/stage6-estimates.md`. У каждого вопроса — вариант по умолчанию: на него можно
ответить «ок». **Блокирующие** помечены; без ответа на них соответствующий подэтап не начинается, остальное идёт по
умолчанию.

## Ответы заказчика

- **Вопрос 1 (цель кадра):** 600 fps.
- **Вопрос 2 (git):** пушить; коммиты — от аккаунта заказчика, без упоминаний ассистента.
- **Вопрос 6 (топология):** «максимальная производительность и параллельность; в геймплейном коде не хранить все
  правки, только несколько последних; в редакторе — все, и при билде сливать их в одну». Принятое решение: редактор
  запекает весь список правок в `SdfBakedLayer`; игра держит `SdfWorld` — запечённую базу и не больше `MaxEdits`
  последних правок, старые вплавляются в базу (`Fold`) и рассылаются воркерам дельтами; меши строит пул воркеров
  (`SdfMeshWorkers`), у каждого реплика мира.
- **Вопрос 13 (физика):** CSPhysics — это и есть форк; дописывать его можно. Сделано: индексированный меш чанка,
  удаление формы, замена формы статики на месте; найден и исправлен баг форка в `Statics.SetShape`.

## Общее

1. **(блокирующий для S6-05)** Цель кадра для SDF-сцен: `task.md` требует 600 fps на ноутбуке, `plan.md` 1.3 — 60 fps на
   среднем десктопном GPU и 30 fps на мобильных. *По умолчанию:* 600 fps — цель perf-стенда на эталонном ноутбуке (с
   апскейлом и приёмами из раздела 20–21), 60/30 fps — минимальные требования на целевых устройствах.
2. Git: `task.md` просит локальную ветку `stage6` и без отправки, среда работы — ветку `claude/sharp-newton-yb7mx5` с
   отправкой. *По умолчанию:* коммиты `SDF: …` в `claude/sharp-newton-yb7mx5`, без pull request.
3. Где живёт SDF-код. *По умолчанию:* отдельный модуль `Modules/Engine/SDF` (`@cse/sdf`), как UI-модуль; движок
   подключает его зависимостью.
4. Единицы и масштаб мира (`plan.md` 16.3). *По умолчанию:* метры; шаг h = 0,1 м для ray marching, 0,2–0,5 м для
   меш-тира; дальность первого уровня — десятки метров.
5. Нужен ли SDF на всех платформах (`plan.md` 14, 16.2). *По умолчанию:* да, но на playable ads и мини-приложениях
   только меш-тир с запечёнными чанками.

## SDF.5 Встраивание в движок

6. **(блокирующий, решён)** Топология воркеров (`plan.md` 9.6): кто держит список правок и где строятся меши.
   *Ответ заказчика:* GameLogic — посредник для скриптов, мир в него не тащить. *Решение:* отдельный SDF-воркер держит
   мир (базу и реплику последних правок) и пул меш-воркеров; GameLogic держит только последние правки (`SdfClient`,
   id сразу) и раз в кадр шлёт дельту и фокус; чанки идут из SDF-воркера по своим портам прямо в рендер и физику.
7. Как сцена объявляет SDF-мир. *По умолчанию:* поле `sdf` в `SceneManifest` (база L0 и список правок) и компонент
   `SdfEditComponent` для правок, которые двигает скрипт (дыра, туннель).
8. Транспорт без `SharedArrayBuffer` (itch.io, Яндекс Игры). *По умолчанию:* только `postMessage` с transferable на
   первом шаге; кольцевой буфер на SAB — позже, для Electron.

## SDF.8 Физика

13. **(блокирующий)** CSPhysics — это и есть «форк Bepu» из `plan.md`? Как в нём заменить статический меш без
    перестройки сцены, и есть ли точка расширения для своей формы (`plan.md` 9.3)? *По умолчанию:* считаем CSPhysics
    тем форком; первый шаг — статические `TriangleMesh` из чанков с двойной буферизацией.
14. Размер WASM физики (`plan.md` 1.2): допустимо ли добавить расчёт расстояния на C#? *По умолчанию:* нет, меши и
    расстояния считаются на TypeScript, в физику идут готовые треугольники.

## SDF.9 Свет

15. Как Babylon 9.29 отдаёт кластерные источники (Forward+, S6-06) в собственный `ShaderMaterial` (`plan.md` 8.2, 27.1).
    *По умолчанию:* SDF-шейдер получает до 8 самых значимых источников uniform-ами, пока S6-06 не даст общий список.
16. Тени между SDF и полигонами (`plan.md` 8.3): нужны ли в обе стороны с первой версии? *По умолчанию:* SDF → SDF и
    полигоны → SDF через карту теней Babylon; SDF → полигоны — после SDF.9.
