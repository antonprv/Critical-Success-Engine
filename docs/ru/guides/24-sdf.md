# 24. SDF-мир

Модуль `Modules/Engine/SDF` (`@cse/sdf`) — мир из signed distance fields поверх Babylon, по `plan.md`: упорядоченный
список правок как единственный источник истины, точное поле на CPU, кэш расстояний в кирпичах, меш-тир для слабых
устройств и ray-marched слой, который делит глубину с обычными мешами Babylon.

```bash
cd src/CSEngine/Modules/Engine/SDF
pnpm dev          # демо: http://127.0.0.1:5177/
pnpm test         # юнит-тесты (100% покрытия на файл)
pnpm test:e2e     # проверка глубины в Chromium (после pnpm build)
pnpm bench        # замеры CPU-части
```

## Список правок

Мир — это список правок (`EditList`). Правка — форма (сфера, бокс, скруглённый бокс, капсула, тор, цилиндр, эллипсоид),
поза и равномерный масштаб, булева операция с тем, что было до неё (объединение, вычитание, пересечение и их гладкие
версии с радиусом `SmoothK`), материал, флаги и режим физики. Порядок важен: операции не коммутативны.

```ts
import { EditList, GroundPlane, SdfField, SdfOp, SdfShape } from "@cse/sdf";

const edits = new EditList();
const field = new SdfField( edits, new GroundPlane( 0 ) );   // L0: земля

edits.Add( { Shape: SdfShape.Sphere, Position: [ 0, 1.6, 0 ], Params: [ 2, 0, 0, 0 ], MaterialId: 1 } );

// дыра, которую можно двигать: обычная правка, а не необратимая мутация
const hole = edits.Add( {
	Shape: SdfShape.Sphere,
	Op: SdfOp.SmoothSubtract,
	Params: [ 0.9, 0, 0, 0 ],
	SmoothK: 0.3,
} );

edits.Update( hole.Id, { Position: [ 1, 0.2, 3 ] } );
```

Каждая правка упаковывается в 64 байта (`PackEdit`), в том же виде, в каком её возьмёт GPU-буфер. Что ещё даёт список:

| | |
|---|---|
| `Version` | растёт с каждым изменением; воркер сообщает, до какой версии догнал |
| `Watch()` | свой поток «изменённых коробок» для каждого потребителя (кирпичи, чанки, физика) |
| `TakeDelta()` / `ApplyDelta()` | изменения одним transferable-буфером для другого воркера; на той стороне те же id |
| `Serialize()` / `EditList.Deserialize()` | сохранение (версионированный бинарный формат; правки-превью не сохраняются) |
| `Candidates( box )` | правки, которые могут что-то изменить в области, по порядку (BVH; пересечения — всегда) |

## Поле

`SdfField` считает расстояние, материал, нормаль (4 выборки по тетраэдру) и рейкаст (sphere tracing только по правкам на
пути луча). Это эталон для геймплея и физики. Для выборки многих точек одной области есть `field.Compile( edits )` —
`SdfProgram`: правки упакованы в один массив, формы и операции встроены в цикл; результат совпадает с `Evaluate`.

```ts
const hit = field.Raycast( [ 0, 5, 10 ], [ 0, -0.3, -1 ], 100 );   // T, Position, Normal, MaterialId или null
const program = field.Compile( edits.Candidates( regionBox ) );
const d = program.Distance( x, y, z );
```

Базовый слой L0 — `GroundPlane` или `NoiseTerrain` (холмы из октав value noise с поправкой Липшица, чтобы луч не
проскакивал склон).

## Кирпичи

`SdfVolume` — один уровень кэша (разделы 5–6 plan.md): окно карты кирпичей M³ вокруг глаза с тороидальной адресацией,
атлас R8 из слотов 10³ (кирпич 8³ ячеек плюс запас под трилинейную фильтрацию), copy-on-write при замене кирпича.
`Update()` берёт изменённые коробки, расширяет их на кодируемый диапазон, помечает ячейки устаревшими и перестраивает
не больше `Budget` ячеек за вызов, ближние к глазу первыми; устаревший кирпич остаётся видимым, пока не готов новый.
`Sample( x, y, z )` читает кэш так же, как GPU (трилинейно).

Для рисования `Materials: true` хранит материалы каждого узла во втором атласе тех же слотов, `RangeSpacings`
расширяет кодируемый диапазон (затенению и мягким теням нужно поле дальше, чем маршу: 8 шагов сетки, как у плотной
сетки), а `Bounds` берёт только мир внутри коробки. `SdfRaymarchLayer` принимает такой объём вместо плотной сетки:
`SdfBrickTexture` передаёт атласы и карту (тексель на ячейку: слот, «твёрдо» или сколько ячеек пустоты вокруг — луч
проходит пустоту длинными шагами), дальше только записанные слоты и карту, если она изменилась, а шейдеры собираются с
`SDF_BRICKS`. На сценах размером с демо это медленнее плотной сетки (два зависимых чтения на шаг: 131 против 88 fps в
1080p) и не меньше по памяти; это основа clipmaps больших миров, где плотный объём не помещается. В демо — `?bricks=1`.

## Меш-тир

`SdfMeshChunks` строит мир треугольниками вокруг центра (игрока): Surface Nets по чанкам с общими границами (без щелей
и двойных граней), нормали по градиенту, запечённый AO, 16-битные индексы. Правка перестраивает только чанки, до
которых дотягивается; чанк, далёкий от поверхности, пропускается одной пробой в центре. Это основной вид мира на
слабых телефонах (раздел 23) и те же чанки, что нужны физике (раздел 9.2).

## В сцене Babylon

```ts
import { DenseSdfGrid, SdfMeshChunks } from "@cse/sdf";
import { SdfMeshLayer, SdfRaymarchLayer } from "@cse/sdf/render";

// тир B: ray marching плотной сетки, глубина пишется в общий буфер
const layer = new SdfRaymarchLayer( scene, new DenseSdfGrid( field, bounds, 160 ) );

// тир C: меши
const meshes = new SdfMeshLayer( scene, new SdfMeshChunks( field, { CellSize: 0.2, ChunkCells: 20 } ) );
scene.onBeforeRenderObservable.add( () => meshes.Update() );
```

`SdfRaymarchLayer` рисует задние грани коробки вокруг сетки; фрагментный шейдер идёт по 3D-текстуре, освещает
попадание в том же проходе (солнце и небо берутся из `DirectionalLight` и `HemisphericLight` сцены, плюс AO и мягкие
тени по полю) и пишет `gl_FragDepth`, поэтому меши перед SDF-поверхностью и за ней сортируются обычным тестом глубины.
`DebugView`: нормали, число шагов на пиксель, полосы расстояния. Нужен WebGL2.

Перед экранным проходом коробка рисуется в цель, где тексель покрывает 8×8 пикселей (`ConeTiles`, по умолчанию `[ 8 ]`;
для нескольких уровней — от крупного к мелкому, `[]` выключает): тексель ведёт один конус вокруг лучей всех своих пикселей,
пока поверхность не окажется ближе радиуса конуса, и каждый луч на экране стартует оттуда (cone marching, plan.md 20.1).
Пустота перед поверхностью проходится один раз на тайл; где конус ничего не встретил, пиксель готов без единого шага.
Каждый пиксель по-прежнему сам находит своё попадание: на неподвижных тестовых сценах картинка совпадает до пикселя, на
рёбрах плиты под скользящим углом отдельный пиксель может выпасть в любую сторону (sphere tracing решает такие пиксели по
тому, куда попали его шаги). В демо: 330 → 565 fps на сцене, где в основном пустота, только марш (`?view=2`) 230 → 350.
Нужны float-цели рендера (`SdfConeMarch.Supported`); без них лучи стартуют от коробки. Оболочки динамических правок тоже
принимают `ConeTiles` (`MeshLayerOptions`), по умолчанию выключено: луч оболочки и так стартует от её сферы, которую правка
почти целиком заполняет, — там лишний проход стоит дороже, чем экономит.

И коробка, и оболочки динамических правок маршатся **шахматкой** (`Checkerboard`, по умолчанию включено; plan.md 21.7, по
мотивам Decima): за кадр маршится половина углов пиксельной сетки — те, у которых x + y + чётность чётно, — в цель, где
тексель — это один угол; чётность меняется каждый кадр, а пиксели на экране собираются из двух своих углов этого кадра и
двух углов, которые маршил предыдущий кадр (репроекция через камеру прошлого кадра, берутся только там, где они видели ту
же поверхность). Половина лучей за кадр, четыре выборки на пиксель, никакого накопления дольше двух кадров (нет шлейфа
TAA); края получаются глаже, чуть мягче. Луч угла строится по самому углу, а не по месту, где растеризуется его тексель, и
проход рисуется с view-projection экрана (Babylon подогнал бы её под форму цели). Замеры: тир B 64 → 93 fps (`light`),
77 → 118 (`showcase`), 552 → 602 (`depth`); оболочки 235 → 259 (`sdf-dynamic-16`), 762 → 801 (`sdf-splats`). Освещение
дешевеет вдвое, марш — меньше чем вдвое (группа лучей маршит, пока не закончит самый длинный, а группы шахматки
охватывают вдвое больше экрана). В движении мерцает не больше, чем без неё. Нужны float-цели рендера, как и для конусов;
`?checker=0` выключает её в демо.

`ChooseTier( DetectCapabilities( gl, "gpu" in navigator ) )` выбирает тир по возможностям устройства, результату
короткого бенчмарка и выбору игрока.

## Запечённая база и последние правки

Редактор хранит все правки, а при сборке запекает их в одно сэмплированное поле — `SdfBakedLayer`: ячейки по 8³
выборок, у ячеек рядом с поверхностью — кирпич 9³ (расстояние и материал по байту), у остальных — только расстояние в
центре (граница снизу, луч по-прежнему шагает крупно). Игра держит `SdfWorld`: эту базу и не больше `MaxEdits`
последних правок. Когда правок больше, самые старые вплавляются в базу (`Fold`: пересэмплируются только ячейки, до
которых правка дотягивается); правки с флагом `Keep` (движущаяся дыра) не вплавляются никогда.

```ts
import { SdfBakedLayer, SdfEditFlags, SdfOp, SdfShape, SdfWorld } from "@cse/sdf";

// сборка в редакторе: весь список правок -> одна база (её же можно сохранить: Serialize)
const base = SdfBakedLayer.Bake( editorField, { Bounds: bounds, Spacing: 0.1 } );

// в игре
const world = new SdfWorld( base, { MaxEdits: 16 } );
const hole = world.Add( { Shape: SdfShape.Sphere, Op: SdfOp.Subtract, Flags: SdfEditFlags.Keep } );
world.Add( { Shape: SdfShape.Sphere, Op: SdfOp.Subtract, Position: hit.Position } );   // копание
```

Вплавления едут в дельтах списка правок, поэтому реплика мира в воркере (`SdfWorld.FromBase` + `ApplyDelta`) вплавляет
те же правки в том же порядке и совпадает с основным миром бит в бит. Для этого все числа правки при входе в список
округляются до float32 — так их видит и упакованная форма, и GPU.

## Меш-тир в воркерах

`SdfMeshWorkers` — тот же меш-тир, но каждый чанк строит один из пула воркеров (по умолчанию ядра минус одно), у
каждого — реплика мира. Пул сам забирает дельты мира и рассылает их, чанки, которых ещё нет, строятся раньше
перестроек, а чанк, который ещё считается, не отправляется повторно. Слою Babylon всё равно, откуда чанки:

```ts
import { CreateMeshWorker, SdfMeshWorkers } from "@cse/sdf";

const chunks = new SdfMeshWorkers( world, { CellSize: 0.2, ChunkCells: 20, Radius: 2 }, CreateMeshWorker );
const meshes = new SdfMeshLayer( scene, chunks );
```

Мешинг пропускает что может (plan.md 21.8, п. 1–2): узлы чанка идут блоками 4³, и блок, центр которого дальше от
поверхности, чем блок достаёт, получает эту одну выборку для всех узлов; остальные блоки считаются только с правками,
которые до них достают (`ChunkOptions.SkipEmpty`, `Region`). Меш тот же, у физики тоже: чанк земли 0,95 → 0,61 мс,
чанк с 37 правками в досягаемости 5,0 → 3,4 мс.

## Уровни детализации

С `Levels` (опция чанков или `Levels` в поле `sdf` сцены) чанки растут с расстоянием: у чанка уровня L ячейки в 2^L раз
крупнее, а самих ячеек столько же. Чанки последнего уровня заполняют `Radius` вокруг центра; ближе каждый делится на свои
восемь следующего, более мелкого уровня, вплоть до уровня 0 примерно в `Radius` чанков от игрока (октодерево, поэтому
чанки разных уровней никогда не перекрываются). Ключи уровня 0 остаются `"x,y,z"`, остальные — `"L:x,y,z"`.

```ts
// ячейки 0,25 м рядом и 4 м на уровне 4: земля в 320 м примерно из 600 чанков
const chunks = new SdfMeshWorkers( world, { CellSize: 0.25, ChunkCells: 16, Radius: 2, Levels: 5 }, CreateMeshWorker );
```

- **Швы.** Там, где встречаются уровни, границы не совпадают, поэтому при нескольких уровнях каждый чанк строит ещё один
  ряд квадов (его меш заходит на полъячейки за его границы со всех сторон: соседи перекрываются) и вешает юбки на две
  ячейки вглубь твёрдого от своих открытых краёв (`Skirts`). Юбки в физику не попадают (`SdfMeshData.SkirtFrom`).
- **Без мигания.** Пока игрок движется, чанк, ушедший из области, рисуется, пока не построено то, что его заменяет;
  чанк, ушедший совсем, убирается сразу. Область перестраивается только после сдвига на восьмую часть чанка.
- **Освещение.** Запечённый AO на всех уровнях шагает ячейкой уровня 0, поэтому на стыке уровней освещение не меняется.
- **Устойчивые тени.** Карта теней солнца стоит на месте, пока её источники тени остаются в коробке, под которую её
  подогнали; при переподгонке размер округляется до шага 2^(1/4), центр — до текселя, а normal bias растёт вместе с
  текселем. Карта, подгоняемая заново каждый кадр, сдвигала тексели по миру, пока чанки появлялись и уходили, и acne на
  каждом склоне ползала.
- **Тени.** В карту теней солнца рисуют только уровни ниже `ShadowLevels` (опция слоя мешей, по умолчанию 2): карта
  подгоняется под свои источники тени, и дальние уровни растянули бы её на весь мир (acne на каждом склоне). Дальние
  тени — работа каскадов (рендер, S6-06). Принимают тень все уровни.
- **Физика.** Получает чанки уровней ниже `PhysicsLevels` (опция сцены, по умолчанию 2): дальние стоили бы ей только
  форм. SDF-воркер занимается областью и пулом не чаще раза в `PoolMs` (4 мс): GameLogic шлёт тик каждый кадр, и работа на
  каждом тике игры без ограничения fps ставила бы тики в очередь быстрее, чем они разбираются.
- **Ограничения.** То, что тоньше ячейки уровня, на этом расстоянии пропадает (плита в 2 м под ячейками в 4 м, тонкая
  башня). Мир под землёй должен быть глубже самой крупной ячейки. `Triangles` слоя мешей — сколько треугольников рисуется
  сейчас (бюджет из plan.md 23.4).

Perf-сцена `sdf-lod`: земля 256 м, пять уровней, камера облетает её на 15 м/с — 647 fps на тестовом ноутбуке, камера
неподвижна — 622 (125 тыс. треугольников).

## Физика

Чанк меш-тира — обычная статика CSPhysics. Физический воркер принимает команды `PhysOpType.SdfChunk` (ключ, позиции
и индексы чанка) и `RemoveSdfChunk`: новый чанк становится статикой, перестроенный меняет форму на месте
(`SetStaticShape`, тела на нём просыпаются), старый меш освобождается.

## SDF в движке

Сцена объявляет SDF-мир полем `sdf` манифеста: запечённую базу (файл сборки редактора по URL или правки, которые
запекаются при загрузке), лимит последних правок и параметры меш-тира. Мир живёт в отдельном SDF-воркере: GameLogic
держит только последние правки и раз в кадр отправляет их дельтой вместе с точкой, вокруг которой строятся чанки
(камера или точка `FocusAhead` перед ней); чанки уходят из SDF-воркера прямо в рендер и в физику.

```ts
export const Level: SceneManifest = {
	id: "level", name: "Level", description: "…",
	sdf: {
		Base: { Url: "levels/level.sdf" },     // или { Bake: { Edits, Ground, Bounds, Spacing } }
		MaxEdits: 16,
		CellSize: 0.25, ChunkCells: 16, Radius: 3,
		FocusAhead: 20,
		Start: [ 0, 0, 0 ],                    // строится первым, до создания сущностей
	},
	entities: [ … ],
};
```

Сцена не создаёт свои сущности, пока SDF-воркер не построит область вокруг `Start` (и для рендера, и для физики),
поэтому тела не проваливаются сквозь землю, которой ещё нет. Пока сцена грузится, воркер строит чанки вокруг
`Start`; ставь её туда, куда будет смотреть фокус камеры. Ожидание сдаётся через 30 с с предупреждением, а мир,
который не загрузился (`LoadError`), не ждут.

Из скрипта — `this.Engine.Sdf`:

```ts
const hole = this.Engine.Sdf.Add( { Shape: SdfShape.Sphere, Op: SdfOp.Subtract, Flags: SdfEditFlags.Keep } );
this.Engine.Sdf.Update( hole.Id, { Position: [ x, y, z ] } );   // id известен сразу
const hit = await this.Engine.Sdf.Raycast( origin, dir );        // ответ через кадр
```

## Свет, тени и затенение

`SdfRenderContext` связывает SDF-мир и меши сцены: у них общая карта теней солнца (меши отбрасывают тень на SDF и
наоборот; карта рисуется не чаще `ShadowHz` раз в секунду), а материал обычного меша получает плагин, который затемняет
его окклюзией SDF-мира (два отсчёта объёма на вершину) и других мешей (каждый меш — сфера). Для SDF-сцены движок делает
контекст сам; `?shadows=off` и `?sdfao=off` на странице выключают и то, и другое для теста.

Тир B выносит две дорогие части света из горячего пути (plan.md 21.8):

- `LightResolution` (по умолчанию 0,5 экрана по каждой оси): `SdfLightBuffer` маршит мягкую тень и затенение в этом
  разрешении; проход в полном разрешении по-прежнему освещает каждый пиксель сам, но эти два множителя берёт из
  четырёх ближайших текселей, видевших ту же поверхность, а где таких нет — маршит сам. 1080p: 94 → 113 fps (`light`),
  112 → 132 (`showcase`).
- `ShadowCache` (по умолчанию включён): `SdfShadowCache` маршит коробку в вид солнца один раз и держит, пока не
  меняются матрица карты теней, коробка, поле и динамические правки; проход тени читает тексель вместо марша. Пока
  правки меняются каждый кадр, кэш не включается. 114 → 133 fps, кадр тот же.

## Динамические правки

Правки, которые двигаются каждый кадр — дыра за тоннельной пушкой, плавающий сгусток, сплэт в полёте, — живут отдельно от
списка правок: ни версии, ни дельты, ничего не вплавляется, не сохраняется и не перестраивается для отрисовки. Их рисует
GPU поверх мира (ray marcher или оболочка вокруг каждой поверх меш-тира), поэтому сдвинуть правку стоит пару uniform'ов.
Одновременно — не больше `MAX_DYNAMIC_EDITS` (16).

```ts
const hole = this.Engine.Sdf.AddDynamic( {
	Shape: SdfShape.Sphere, Op: SdfOp.SmoothSubtract, Params: [ 1.5, 0, 0, 0 ], SmoothK: 0.4,
	Flags: SdfDynamicFlags.Physics,   // по желанию: физика её тоже чувствует
} );
this.Engine.Sdf.UpdateDynamic( hole.Id, { Position: [ x, y, z ] } );   // каждый кадр, бесплатно
this.Engine.Sdf.RemoveDynamic( hole.Id );
```

С `SdfDynamicFlags.Physics` SDF-воркер перестраивает чанки, до которых дотягивается правка, только для физики (никогда
для отрисовки), с правкой, не чаще 20 раз в секунду и только когда физика забрала прошлые: шары падают в движущуюся дыру
и катятся по движущемуся сгустку. Чанки, которые правка покинула, получают свои меши обратно.

## Слои и маски

У правки есть `Layer` (один бит из восьми) и `Mask` (слои, с которыми она сливается; по умолчанию все). Если в маске
правки есть слой поверхности, которую она встречает, они сливаются: гладкое объединение заполняет шов галтелью, а
материалы плавно перетекают друг в друга на ширине `SmoothK`. Если нет — встречаются с жёстким швом и сохраняют свои
материалы, но по-прежнему отбрасывают друг на друга тени и окклюзию. Вычитание (`Subtract`) режет только слои своей маски.

```ts
world.Add( { Shape: SdfShape.Torus, Layer: 2, Mask: 2, MaterialId: 4 } );   // тор, который не сливается с остальным
```

Динамические правки и сплэты принимают те же `Layer` и `Mask`.

## Сплэты

Сплэт — мягкий сгусток, который прилипает там, куда попал (краска, грязь, слизь). В движке это сущность с `Projectile`
и `SdfSplat`. В полёте — динамическая правка, вытянутая вдоль скорости; там, где снаряд попал, `Engine.Sdf.Splat`
оставляет обычную правку — эллипсоид, сплющенный по поверхности (`SplatEdit`: объём сохраняется, чуть утоплен), слитый
с тем, во что попал, если позволяют слои. Сплэтов может быть сколько угодно: старые вплавляются в базу.

```ts
Ent( "Splat", [
	Comp( Projectile, { Radius: 0.15, ApplyGravity: true } ),
	Comp( SdfSplat, { Radius: 0.22, MaterialId: 2, Layer: 1, Mask: ALL_LAYERS } ),
] );
```

## Трава из сплэтов

`sdf.Grass` в манифесте сцены выращивает траву на SDF-мире: травинки рассыпаны по поверхности там, где её материал из
`OnMaterials`, и рисуются thin instance'ами тайлами по 8 м (тайл вне кадра не рисуется, дальний — только часть травинок,
дальше `LodDistance`). Всё, что движется по ней — каждый меш контекста как сфера, — приминает травинки от себя; они
поднимаются за `Recover` секунд. Динамическая правка, которая убирает землю, убирает и траву. Если в маске травы есть
слой земли, корни плавно переходят в цвет земли.

```ts
sdf: { …, Grass: { Bounds: [ -13, -13, 13, 13 ], Density: 40, Height: 0.35, Recover: 2.5 } },
```

## Кривые, тела, кратеры

Трубка вдоль кривой — червяк, корень, кабель; с Op Subtract — тоннель — это по скруглённому конусу на кусок
(SdfShape.RoundCone: отрезок со своим радиусом на каждом конце). Каждый кончается сферой, с которой начинается следующий,
поэтому швов нет:

```ts
this.Engine.Sdf.AddCurve( {
	Points: [ [ 0, 0.3, 0 ], [ 3, 0.8, 1 ], [ 6, 0.3, 0 ] ],   // сплайн Катмулла-Рома через них
	Radii: [ 0.3, 0.5, 0.2 ],                                   // радиус в каждой точке
	MaterialId: 4,
} );
```

`SdfWorm` выращивает такую: голова бродит от места сущности и каждые `Piece` метров кладёт кусок (настоящие правки:
физика их чувствует, старые вплавляются в базу). `SdfBody` рисует сущность формой SDF-мира, которая следует за её
трансформом: поставь его на твёрдое тело того же размера — и куб, которого толкает физика, сливается с полом, скользя по
нему. `SdfSplat` с `Carve` забирает материю там, куда попал: кратер глубже, чем шире; выстрелы в одно место пробивают
насквозь.

Когда поверхность возвращается над телами (ушла движущаяся дыра, которую чувствовала физика), физический воркер
выталкивает оказавшиеся внутри неё тела вверх — шаг за шагом, тем быстрее, чем глубже они (от 1 до 8 м/с), без телепорта.
«Внутри» значит, что первая поверхность прямо над телом, в любом чанке, смотрит вверх; под нависанием она смотрит вниз, и
тело остаётся на месте. За пределами построенной области (`Radius` чанков вокруг фокуса) под телами ничего нет:
держи игру внутри неё или огороди.

## Фракталы

Базой может быть формула вместо запекания: `MandelbulbBase` (степень, итерации, константа Julia, инверсия в сфере —
«внутри Мандельброта», мир по умолчанию фрактальных шаблонов: `InvertedMandelbulb()`). Поле — оценка по уходу орбиты
0,5 r ln r / dr, переведённая в мировые единицы масштабом инверсии (она конформна) и ограниченная снизу у центра. У базы
нет границ, поэтому старые правки мира вплавляются в `SdfSparseLayer`: выборки хранят только задетые ячейки, везде
остальное считает формула. Базы передаются как `SdfBaseDescriptor` (воркеры, сохранения, сцены: сцена движка пишет
`Base: { Analytic: InvertedMandelbulb( 20 ) }`). Сэмплеры передают детализацию, которую могут удержать
(`SdfProgram.Detail`: чанк — свою ячейку, сетка — свой шаг), и орбита останавливается там, где следующая итерация
добавила бы только мелкий шум. В демо пещера — `?scene=fractal`; стенд `sdf-fractal` — 759 fps.

У фрактала нет известного пола: `FindStandingPlace( field, near )` находит его — точки по спирали от заданной, каждая
опускается на пол под собой, пол должен смотреть вверх и оставлять место для тела, — а сцена движка просит об этом
через `StartOnSurface` (место мешится первым и возвращается как `Sdf.Start`; позже — `Sdf.FindStandingPlace`).
Точечные источники (до четырёх) освещают марш SDF так же, как стандартные материалы Babylon освещают меши: фонарь в
пещере.

### Язык формул

Фрактал можно записать формулой (`FormulaBase`, дескриптор `{ Kind: "Formula", Options }`): один исходник
компилируется в JavaScript для CPU (мешинг, физика, лучи; vec3 — три числа, ни одной аллокации на выборку) и в GLSL
для GPU (`SdfFormulaVolume`: марш вычисляет формулу как есть, параметры — uniform). Формула — несколько блоков над
состоянием орбиты: `z` и `c` (vec3, оба начинаются с точки), `dr` (начинается с 1), только для чтения `p`, `r` (|z|), `i`:

```
param float power = 8 in [2, 16];   // параметры: float или vec3, значение по умолчанию, диапазон для редактора
init { c = vec3(0.2, 0.6, 0.1); }   // один раз (необязателен): здесь — множество Жюлиа
iterate {                           // каждую итерацию
	float theta = acos(clamp(z.z / max(r, 1e-30), -1, 1)) * power;
	float phi = atan(z.y, z.x) * power;
	float rp = pow(r, power - 1);
	dr = rp * power * dr;
	z = rp * r * vec3(sin(theta) * cos(phi), sin(theta) * sin(phi), cos(theta)) + c;
}
distance { return 0.5 * log(r) * r / dr; }   // необязателен: это значение по умолчанию
```

Операторы: локальные `float` / `vec3`, `=`, `+=`, `-=`, `*=`, `/=` (float растягивается на vec3 в `*=` и `/=`), `if` /
`else`, `return` в `distance`. Функции: abs, sign, floor, fract, sqrt, sin, cos, tan, asin, acos, exp, log, min, max,
mod, pow (от |x|, как на GPU), atan(y, x), clamp, mix, length, dot, cross, normalize, vec3. Ошибка — `FormulaError`
со строкой и колонкой. Рамка вокруг каждой формулы (`FractalFrameOptions`) ставит и масштабирует её, выворачивает
инверсией, обрезает итерации по детали и смешивает два материала по orbit trap. Пресеты (`FormulaPresets`):
перевёрнутый Мандельброт (`InvertedMandelbrot()`, мир по умолчанию), Mandelbulb, Mandelbox, губка Менгера. Сквозная
проверка маршит те же пиксели на CPU: картинка GPU расходится с ним на 0,35 % (силуэты).
