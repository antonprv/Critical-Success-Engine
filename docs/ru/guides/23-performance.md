# 23. Производительность: perf-стенд

`pnpm perf` (в `src/CSEngine/Core`) измеряет, насколько быстро движок отрисовывает каждую тестовую сцену в настоящем
Chromium на этой машине без ограничения частоты кадров, и пишет отчёт. Цель — **600 кадров в секунду** в каждом сценарии
на целевом ноутбуке (`task.md`, S6-05).

```bash
cd src/CSEngine/Core
pnpm perf                              # все сценарии
pnpm perf -- --only coin-hunt,interop  # только некоторые
pnpm perf -- --runs 5 --seconds 15 --warmup 5
pnpm perf -- --update-baseline         # сохранить результаты как новую базу
pnpm perf -- --params aa=msaa          # эксперимент: дополнительные переключатели страницы
```

Стенд собирает каждый проект как `pnpm build` (с настоящей физикой и C#-скриптами), раздаёт его, открывает сцену каждого
сценария в **окне** Chromium (headless-Chromium рисует программно, через SwiftShader, и GPU им не измерить), прогревает
сцену, а потом меряет несколько отрезков времени и берёт медиану. В корне репозитория появляются:

| | |
|---|---|
| `perf/results/<время>.json`, `latest.json` | все числа по всем отрезкам |
| `perf/baseline.json` | база для сравнения: частота кадров ниже неё больше чем на 5 % — регрессия (команда завершается с ошибкой) |

`PERF_CHROMIUM_PATH` задаёт браузер (по умолчанию системный Chromium). Chromium запускается без
`--disable-frame-rate-limit` и `--disable-gpu-vsync`: `?uncapped` и так не привязан к частоте экрана, а с этими флагами
композитор Chromium занимает целое ядро, отнимая его у воркеров игры.

## Что измеряется

- **fps** — кадры с **новым состоянием игры** в секунду. Рендер может рисовать чаще (он не связан с игровой логикой
  напрямую) и тогда перерисовывает то же самое состояние. Эта частота идёт в отчёт как «draw loop fps», но частотой кадров
  игры не считается.
- **1 % low / 0,1 % low** — частота самых медленных 1 % (0,1 %) кадров: то, как ощущаются подёргивания.
- Время кадра p50 / p95 / p99; время CPU потока рендера на кадр, число вызовов отрисовки и треугольников; время игровой
  логики на кадр и на вызов C#; время шага физики и число тел; куча JS страницы и кучи .NET.

Числа даёт сам движок. Каждый воркер копит замеры в кольцевых буферах (`Source/Engine/Diagnostics/PerfProbe.ts`: один
`performance.now()` и одна запись в массив на замер), а стенд забирает их через
`worker.evaluate( () => __csePerf.Take() )`. GPU и строка рендерера указаны в шапке отчёта.

## Переключатели страницы

| | |
|---|---|
| `?scene=<id>` | начать с этой сцены, а не с первой (удобно и при работе над одной сценой) |
| `?uncapped` | без ограничения частоты кадров: цикл рендера рисует, как только приходит новое состояние игры, держа на GPU не больше четырёх кадров одновременно, а не подстраивается под экран |
| `?aa=msaa`, `?aa=off` | сглаживать края мультисэмплингом (MSAA) вместо прохода FXAA по умолчанию или не сглаживать вовсе. FXAA стоит по умолчанию: на слабом GPU мультисэмплинг дороже всего в тяжёлых сценах (2000 шаров: 490 кадров/с с MSAA, 690 с FXAA) |

## Сценарии

Сцены Games Sample и нагрузочного проекта (`src/Perf/PerfSuite`):
- `empty` — пустая сцена;
- `entities-10k` — 10 000 статичных коробок;
- `static-100k` — один меш из 100 352 треугольников;
- `physics-2000` — 2000 шаров, которые перемешивает лопасть, чтобы они не засыпали;
- `interop` — TypeScript и C# вызывают друг друга по 500 раз за кадр;
- `ui-heavy` — 120 надписей, меняющихся каждый кадр.

Сценарии из `task.md` для систем, которых ещё нет (CSTables, keyframes, Forward+, BSP, SDF, Electron-сборка), стоят в
отчёте строками «not measurable yet». Свой сценарий — одна строка в `src/CSEngine/Core/Perf/Scenarios.mjs`: проект, сцена
и, при необходимости, `Act( page )`, чтобы что-то сделать в сцене перед замером.
