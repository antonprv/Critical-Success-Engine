## До / после

**До:** `app.ts` синхронно импортировал `game/Game.ts`, который создавал Babylon `Engine`/`Scene` прямо на `<canvas>`
главного потока и использовал стандартный плагин Havok (WASM) от Babylon для физики, если и когда его добавляли. Один

**После:** `app.ts` запускает `src/workers/orchestrator.ts`, который владеет только четырьмя экземплярами `Worker` и

`AudioContext`, изменение размера окна). Всё остальное переехало в свой воркер:

|---|---|---|

| `gamelogic.worker.ts` | реестром сущностей, обработкой ввода, геймплеем/ИИ | рендером, внутренностями физики |

## Почему именно эти четыре, а не больше/меньше

Вы выбрали «максимальное разделение - один воркер на систему» вместо запрошенного роутера.
Четыре воркера выше - это системы, которые сейчас есть в этой кодовой базе. Если позже вы добавите пятую систему
(стриминг/предзагрузка ассетов, сеть, отдельный воркер ИИ/поиска пути), дайте ей свой файл и своё ребро
`MessageChannel` к тому воркеру, которому нужен её вывод: `wireWorkers` в `orchestrator.ts` -
единственное место, где создаются каналы и раздаются порты, так что это единственный файл, которого касается подключение нового воркера.

## Почему передача сообщений, а не SharedArrayBuffer

Вы выбрали `postMessage`/structured-clone вместо `SharedArrayBuffer` + Atomics.
Этот компромисс простыми словами:

- **Что вы получаете**: не нужны заголовки ответа COOP/COEP нигде, где размещена игра
  (`Cross-Origin-Opener-Policy: same-origin` +
  `Cross-Origin-Embedder-Policy: require-corp` - их легко забыть, легко сломать,
  добавив потом один сторонний `<script src>`, и они вне вашего контроля, если
  вы когда-нибудь разместите игру на платформе, не позволяющей задавать заголовки ответа).
- **Чего это стоит**: каждая пачка трансформов, команда создания и событие
  копируется (structured clone) между мирами воркеров на каждом такте, вместо того чтобы
  несколько потоков читали одну и ту же память. При том количестве сущностей, с которым имеет дело
  однопользовательская веб-игра вроде этой, эта цена вряд ли имеет значение; если сообщения с пачками трансформов
  когда-нибудь появятся в профайлере как узкое место, решение - объекты `Transferable` (отправлять нижележащий
  `ArrayBuffer` массива `Float64Array` через `postMessage(msg, [buffer])`, а не обычный массив -
  без копирования и по-прежнему без SharedArrayBuffer/Atomics/COOP/COEP), прежде чем браться за разделяемую память.

## Почему физика - настоящий BEPU через WASM, а не JS-библиотека физики

Вы специально просили перенести интеграцию Bepu из вашего проекта на Godot, а не брать
Rapier/Cannon и т.п. `physics-wasm/` компилирует ваш настоящий
`Framework.Physics` + вендорные `BepuPhysics`/`BepuUtilities` (скопированные из
`Setup.7z`) в браузерный wasm-модуль через workload `wasm-tools` из .NET 8, а
`physics.worker.ts` вызывает его через `[JSExport]`
(`physics-wasm/Bridge/PhysicsBridge.cs`). Реальные шаги сборки и, что важно, оговорки - в
`physics-wasm/BUILD.md`: **я сам это не собирал и не запускал** (в песочнице, где я писал код,
не было доступа к NuGet), так что считайте wasm-часть непроверенной, пока не пройдёте
smoke-тест из BUILD.md.

`physics.worker.ts` корректно деградирует, если wasm-модуль не загрузился
(пишет ошибку в лог и перестаёт шагать), а не роняет остальные три воркера -
это удобно, чтобы дорабатывать рендер и геймплей до того, как появится сборка физики.

## Поток сообщений (текущий)

```
PhysicsWorker (setInterval + аккумулятор, фиксированные 60 Гц)
  -> PhysicsWorld.Step(dt)                            [вызов wasm, в том же потоке]
  -> postMessage(снимок шага: тела, персонажи, перекрытия)   -> GameLogicWorker
GameLogicWorker (такт физики)
  -> OnPhysicsSync -> колбэки перекрытий -> OnPhysicsUpdate у каждого компонента
  -> postMessage({ commands: [...] }) обратно в PhysicsWorker       (одна пачка за такт)

RenderWorker (такт дисплея, раз на показанный кадр, не более 2 ожидающих)
  -> "frame-request"                                  -> GameLogicWorker
GameLogicWorker (такт рендера)
  -> OnInputUpdate -> Update -> OnUIUpdate у каждого компонента
  -> "Frame": интерполированные позы всех отрисовываемых объектов + поза камеры  (Transferable-буфер)
RenderWorker рисует последний полученный кадр.
```

Шаги физики и кадры рендера развязаны. Интерполяция между двумя последними позами физики происходит в GameLogic
(`Transform.WriteInterpolated`), так что воркер рендера просто применяет то, что ему сказали.

## Инструменты разработки

Inspector от Babylon (`scene.debugLayer`) создаёт собственную DOM-надстройку и
требует `document`, которого нет в воркере. По этой причине он не подключён в
`render.worker.ts`. Если хочется вернуть его на время разработки, есть два пути:

1. Оставить второй, не воркерный путь запуска именно для `pnpm dev` (импортировать
   старую прямую настройку Babylon из `Game.ts` вместо оркестратора, когда
   `__DEV__` равно true), смирившись с тем, что dev и prod тогда расходятся по структуре.
2. Пересылать всё, что нужно Inspector для осмотра, обратно в главный поток и
   рисовать там собственный отладочный UI, не Babylon Inspector (больше работы,
   зато dev и prod используют одно и то же разделение на воркеры).

Ни один из них не реализован - `Game.ts` оставлен в репозитории (помечен как вытесненный)
специально, чтобы вариант 1 был небольшим диффом, если он вам понадобится.

## Известные пробелы

- Весь API `PhysicsWorld` открыт через `PhysicsBridge`. `PhysicsBridge.cs` проверен компилятором на
  настоящих исходниках Integration/Bepu (только C#, референсные сборки net8); сама сборка browser-wasm
  (`dotnet workload install wasm-tools`, net10) и поведение в браузере автором этого изменения НЕ запускались -
  соберите её по `Physics/Bridge/BUILD.md` и пройдите тестовую сцену с персонажем, прежде чем доверять.
- Экран загрузки показывает прогресс загрузки сцены, а не реальный прогресс фоновой загрузки ассетов.
- Ход персонажа, который пришёл после того, как его шаг уже выполнился, пропускается (команды потребляются ровно один раз); это
  заметно только после затора, когда воркер физики догоняет сразу несколько шагов.
