# Многопоточная архитектура

Движок работает в странице (главный поток) и шести воркерах. Здесь описано, кто чем владеет, почему разделение именно такое и что
учитывать, прежде чем на него полагаться. Код - в `src/CSEngine/Core/Source/Workers`; модель скриптинга и сцен - в
[ENGINE_ARCHITECTURE.md](ENGINE_ARCHITECTURE.md) и в [гайдах](guides/00-index.md).

## Кто чем владеет

| Поток | Владеет | Не владеет |
|---|---|---|
| главный поток (`App.ts`, `Orchestrator.ts`) | DOM-слушателями (клавиатура, указатель, pointer lock, размер окна), воспроизведением через `AudioContext`, отрисовкой состояния UI (Vue/Quasar) | состоянием игры, физикой, рендером |
| `RenderWorker.ts` | OffscreenCanvas, Babylon `Engine`/`Scene`, мешами, `AssetLoader` | состоянием игры, физикой |
| `PhysicsWorker.ts` | симуляцией CSPhysics (через wasm-мост), шагами с фиксированным интервалом | объектами мешей, правилами геймплея |
| `GameLogicWorker.ts` | сущностями, компонентами, сценами, состоянием ввода, тактами кадра и физики | рендером, внутренностями физики |
| `AudioWorker.ts` | декодированием звука | воспроизведением (оно в главном потоке) |
| `UiWorker.ts` | состоянием и логикой меню / экрана загрузки (`Workers/Ui/UiController.ts`) | отрисовкой (состояние рисует Vue в главном потоке) |
| `SdfWorker.ts` | SDF-миром сцены (запечённая база, реплика последних правок), пулом мешинг-воркеров, ответами на рейкасты | скриптами (они в GameLogic), рендером и физикой (им он шлёт чанки) |

`Workers/Orchestrator.ts` запускает воркеры, `Workers/OrchestratorUtils/GameWorkers.ts` соединяет их: главный поток говорит с каждым воркером, а
у GameLogic есть прямой `MessageChannel` к воркерам рендера, физики, звука, UI и SDF (порт 1 уходит в GameLogic, порт 2 - другому воркеру).
У SDF-воркера свои каналы к рендеру и физике: чанки SDF-мира идут туда напрямую, минуя GameLogic, где работают скрипты.
Типы сообщений лежат в `Workers/Protocol/`. Новая система (стриминг ассетов, сеть, воркер поиска пути) получает свой файл и свой канал к
тому, кому нужен её вывод; каналы создаются в одном месте - `GameWorkers`.

## Почему сообщения, а не SharedArrayBuffer

Движок использует `postMessage` / structured clone, а не `SharedArrayBuffer` + Atomics. Простыми словами:

- **Что вы получаете**: не нужны заголовки ответа COOP/COEP нигде, где размещена игра (`Cross-Origin-Opener-Policy: same-origin` +
  `Cross-Origin-Embedder-Policy: require-corp`). Их легко забыть, легко сломать, добавив один сторонний `<script src>`, и они вне вашего
  контроля на платформе, не позволяющей задавать заголовки ответа.
- **Чего это стоит**: каждая пачка трансформов, команда создания и событие копируются между мирами воркеров на каждом такте, вместо того чтобы
  несколько потоков читали одну и ту же память. При количестве сущностей однопользовательской веб-игры это вряд ли имеет значение. Если сообщения с
  трансформами когда-нибудь появятся в профайлере, первым шагом будут объекты `Transferable` (отправлять нижележащий `ArrayBuffer` массива
  `Float64Array` через `postMessage(msg, [buffer])` - без копирования и по-прежнему без SharedArrayBuffer и COOP/COEP), прежде чем браться за разделяемую память.

## Почему физика - настоящий CSPhysics через WASM

Физика - настоящий CSPhysics, а не JS-библиотека: `Modules/Physics/Bridge` компилирует `Physics.Integration` движка (с вендорными `CSPhysics` /
`CSPhysics.Utilities` и `FastMath`) в браузерный wasm-модуль через workload `wasm-tools` из .NET, а `Workers/Physics/PhysicsWorld.ts` - единственное место,
которое его вызывает (методы `[JSExport]` из `PhysicsBridge.cs`). Как собрать: `devops/build-physics.sh` (или `build-all` без `--skip-physics`),
подробности - в `Modules/Physics/Bridge/BUILD.md`.

`PhysicsWorker.ts` корректно деградирует, если wasm-модуль не загрузился: сообщает об ошибке, игра показывает тост и продолжает без симуляции, а
остальные воркеры работают. Это удобно, чтобы дорабатывать рендер и геймплей без сборки физики.

## Поток сообщений

```
PhysicsWorker (setInterval + аккумулятор, фиксированные 60 Гц)
  -> PhysicsWorld.Step(dt)                            [вызов wasm, в том же потоке]
  -> postMessage(снимок шага: тела, персонажи, перекрытия)   -> GameLogicWorker
GameLogicWorker (такт физики)
  -> OnPhysicsSync -> колбэки перекрытий -> OnPhysicsUpdate у каждого компонента
  -> postMessage({ commands: [...] }) обратно в PhysicsWorker       (одна пачка за такт)

RenderWorker (такт дисплея, раз на показанный кадр, не более 2 ожидающих)
  -> "frame-request"                                  -> GameLogicWorker
GameLogicWorker (такт рендера)
  -> OnInputUpdate -> Update -> OnUIUpdate у каждого компонента
  -> "Frame": интерполированные позы всех отрисовываемых объектов + поза камеры  (Transferable-буфер)
RenderWorker рисует последний полученный кадр.
```

Шаги физики и кадры рендера развязаны. Интерполяция происходит в GameLogic (`Transform.WriteInterpolated`), так что воркер
рендера просто применяет то, что ему сказали. Каждый трансформ, которым управляет физика, хранит четыре последние позы с
номерами шагов, а кадры рисуются в момент `Time.RenderStep`: на полтора шага позади самого нового шага, время идёт плавно
вместе с кадрами (быстрее при отставании, медленнее при опережении, никогда назад; скачком — только после долгой паузы).
Воркер физики шагает по таймеру и догоняет пачками, поэтому шаги приходят с опозданием или по нескольку сразу; при рисовании
по времени шагов ни то, ни другое не видно.

## Инструменты разработки

Inspector от Babylon (`scene.debugLayer`) создаёт собственную DOM-надстройку и требует `document`, которого нет в воркере, поэтому
`SetInspectorVisible` в воркере рендера намеренно ничего не делает. Если хочется Inspector на время разработки, есть два пути:

1. Оставить второй, не воркерный путь запуска именно для `pnpm dev` (прямая настройка Babylon на canvas страницы вместо оркестратора), смирившись с тем,
   что dev и prod тогда расходятся по структуре.
2. Пересылать всё, что нужно Inspector, обратно в главный поток и рисовать там собственный отладочный UI (больше работы, зато dev и prod используют одно
   и то же разделение на воркеры).

Ни один из них не реализован.

## Известные пробелы

- Экран загрузки показывает прогресс загрузки сцены, а не реальный прогресс фоновой загрузки ассетов.
- Ход персонажа, который пришёл после того, как его шаг уже выполнился, пропускается (команды потребляются ровно один раз); это заметно только после
  затора, когда воркер физики догоняет сразу несколько шагов.
