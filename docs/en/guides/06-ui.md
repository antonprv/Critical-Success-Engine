# 06. UI

In a browser, workers have no DOM, and Vue and Quasar can't live without a DOM. So the interface is split the same way as sound:

```
GameLogic ──(scenes, loading progress, HUD, toasts)──▶ UiWorker ──(state patches)──▶ main thread: Vue/Quasar ──draws
GameLogic ◀──(load-scene, set-capture)────────────── UiWorker ◀──(pointerlockchange, clicks)── main thread
```

- **UiWorker** (`Workers/Ui/UiController.ts`) keeps the *state* and the *logic*: what to show (loading / menu / HUD) and when
  the game gets the mouse. It's pure TypeScript with no DOM - it is tested (`Tests/UiController.test.ts`).
- **The main thread** only *draws* the state (`Source/Ui/*.vue`) and forwards DOM events. It has no game logic.
- **The game's scripts** know nothing about the UI worker or Vue - they call `this.Engine.Ui`.

## What `this.Engine.Ui` can do from a script

```ts
ui.SetHud("score", `Score: ${n}`);                 // a line of text at the top left; the key → each component gets its own line
ui.SetHud("score", null);                          // remove the line
ui.SetBar("hp", "HP 40/100", 0.4);                 // a bar (0..1) with a caption; SetBar("hp", "", null) - remove
ui.Toast("Picked up a key");                       // a popup message at the top right
ui.ClearHud();                                     // erase everything (happens by itself on a scene change)
```

HUD updates are usually put in `OnUIUpdate(ui, dt)`. Changes accumulate and are sent in a batch no more than 10 times a second.

## The pause menu, the mouse and loading (how it works)

1. At startup the loading screen is visible (`LoadingOverlay.vue`, the `XpProgress.vue` progress bar); the progress is sent by `SceneManager` as the scene loads.
2. The scene has loaded → the UI asks the browser to capture the mouse (`requestPointerLock`).
3. The browser allowed it → `playing`: the menu is hidden, input is enabled for the game. It **didn't allow** it (a user click is needed) → the menu with a **Play** button.
4. **Esc** - the browser releases the mouse by itself; the UI sees this, opens the menu and turns off the game's input.
5. You picked a scene → the loading screen → mouse capture again. If the browser refused (the click was a while ago) - the menu with a **Resume** button: one click and the game is yours.

If the game itself reloads the scene (a restart with `R`, as in Coin Hunt) while the mouse stays captured, the UI goes straight back
to `playing` - the menu doesn't flash.

It would be nice to "press Esc once more to go back" - that won't work: while the mouse is captured, the browser doesn't give the page Esc. So returning is done by a click.

## Adding a health bar - the full path

This is an example of **how to extend the UI with your own widget**. The bar is already in the engine (`SetBar`); here's how it was added - any other widget
(an ammo counter, a crosshair, a map…) is added by the same scheme. There are just five places:

**1. The protocol** - a message type in `const enum UiMsg` (`Workers/Common/CommonEnums.ts`), and in `Workers/Protocol/UiProtocol.ts`
the data type, a place in the state and the message itself from GameLogic:

```ts
// CommonEnums.ts, in UiMsg (the GameLogic -> UiWorker section):
Bars,

// UiProtocol.ts:
export interface UiBar { id: string; label: string; value: number; }
export interface UiHudState { visible: boolean; lines: string[]; bars: UiBar[]; }
// … in GameLogicToUiMessage:   | { type: UiMsg.Bars; bars: UiBar[]; }
```

**2. The service for scripts** - `Engine/Services/UiService.ts`: `SetBar(...)` puts the data into a dictionary, `Flush()` sends the changes with the `UiMsg.Bars` message.

**3. The UI logic** - `Workers/Ui/UiController.ts`: receives the message and updates the state (if the widget depends on the phase - for example, hide it on pause - decide it here):

```ts
case UiMsg.Bars:
	this._state.hud = { ...this._state.hud, bars: message.bars };
	this.PushState({ hud: this._state.hud });
	break;
```

**4. Rendering** - `Ui/components/Hud.vue` receives `bars` and draws them with the `XpProgress` component (green blocks, like when copying files in XP); `Ui/App.vue` passes them as a prop.

**5. Use** in a script (working code - `Core/Source/Examples/HealthBar.ts`):

```ts
import { Component } from "../../Engine/Core/Component";
import type { UiService } from "../../Engine/Services/UiService";

/** Hit points with a bar on the HUD. Anything that wants to hurt this entity calls `Damage`. */
export class Health extends Component {
	public Max = 100;
	public Current = 100;

	public Damage(amount: number): void {
		this.Current = Math.max(0, this.Current - amount);
	}

	public override OnUIUpdate(ui: UiService): void {
		ui.SetBar("hp", `HP ${this.Current}/${this.Max}`, this.Current / this.Max);
	}
}
```

```ts
Ent("Hero", [Comp(Health, { Max: 100, Current: 60 })]),
// somewhere in a trap:   hero.GetComponent(Health)?.Damage(10);
```

The principle: **data flows one way, events the other**. A script knows nothing about Vue; Vue knows nothing about the game;
between them there are only typed messages. It's good when a widget fits into "data → rendering". If a widget is *interactive*
(a button that changes the game), add one more message in the opposite direction (`UiToGameLogicMessage`) and handle it in `GameLogicRuntime.OnUiMessage`.

## The menu: how to add your own button

The list of scenes in the menu is taken from `SceneRegistry` automatically (the `name` and `description` fields of the manifest). One more button (say, "Settings")
is added the same way as the bar: a field in `UiMenuState` → rendering in `PauseMenu.vue` → a message like `{ type: UiMsg.OpenSettings }` (a new member of `UiMsg`)
in `UiProtocol` → a handler. The `PauseMenu.vue` file is a Windows XP-style window: a title bar, a task pane on the left (the Play button is there), the scene list
as an Explorer-style table (`q-list`/`q-item` from Quasar) and a status bar. Put a new button in the task pane on the left.

## Styling: Windows XP

The engine's identity is an early-2000s desktop: Windows XP chrome (Luna), the office programs of that time and the rhythm of jungle:

- the loading screen is the XP boot screen: a black background, the title, a capsule with blue progress blocks, the engine's name in the bottom right corner;
- the menu is an XP Explorer-style window (a blue task pane on the left, the scene list as a table, a status bar) over a blue
  desktop, through which the paused game is visible; at the bottom is a taskbar with a clock and a green level indicator
  in the tray, blinking at the tempo of jungle (174 BPM);
- the HUD is an XP yellow tooltip in the corner; toasts are tray balloons (`Notify` from Quasar, set up in `Ui/CreateUi.ts`).

Colours and fonts are CSS variables in `Ui/styles/theme.css` (`--xp-blue`, `--xp-beige`, `--xp-desktop`, `--xp-green`, `--xp-font`…): take new elements
from there so the styling stays consistent. The fonts are the same as in XP - Tahoma and Trebuchet MS (Windows has them; on other
systems similar ones are substituted). Animations are turned off if the system has "reduce motion" enabled.

The game screen (HUD and toasts) has no red or orange: the E2E tests look pixel by pixel for the orange ball and the red player
marker in the picture, and interface elements in those colours would give false positives.

Quasar components (`q-list`, `q-item`) are connected automatically by their use in templates; there's no need to import them by hand.

## UI documents instead of Vue screens

The path through the `UiWorker` and Vue described above is the base layer. In projects with the UI plugin enabled (all the templates) the pause menu, the loading screen and the game's HUD are UI documents drawn in the UI Designer and shown from scripts through `GetGameUi()` (guide 13); the Vue screens (`PauseMenu.vue`, `LoadingOverlay.vue`) stay as a fallback for when the plugin isn't there. For your own HUD it's usually easier to draw a document (like `CoinHuntHud.ui.json` in the Coin Hunt template, guide 07) than to add a widget to the protocol.

## If it doesn't work

| Symptom | Cause |
|---|---|
| The HUD is empty | Lines are set only from `OnUIUpdate`/`Update`; check that the component is enabled; the HUD is hidden while the menu is open or loading is in progress |
| A toast doesn't appear | They go through the UiWorker; if the worker crashed - look in the console |
| Right after a scene loads the "Resume" menu appears | The browser didn't give the mouse without a fresh click - this is normal, one click is needed |
| Esc doesn't return to the game | See above - return by clicking **Play/Resume** |
| You need to change the look of the menu/HUD | Only `Source/Ui/**/*.vue`; don't touch the logic (when to show what), it's in `UiController` |
